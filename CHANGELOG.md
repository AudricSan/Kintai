# Changelog

🌐 **English** · [Français](docs/i18n/CHANGELOG.fr.md) · [日本語](docs/i18n/CHANGELOG.ja.md)

All notable changes to Kintai are documented here.

## [Unreleased]

### Security
- **Breaking (API)**: `/api/v1/*` now enforces RBAC authorization — until now, any authenticated token (including a plain employee's) could read and modify every resource of every store. A new `ApiPermissionMiddleware` (after `ApiAuthMiddleware` on the `/api/v1` group) checks each route against a declarative `config/api-permissions.php` map (route name → `PermissionCatalog` key, with an optional "self" rule letting users access their own sub-resources — own profile, own prefs/rates/iCal tokens — without any permission). When the request targets a store (`store_id` route param, query param, or body field), the permission must be granted **for that store** (or through a global-scope role); otherwise holding it anywhere suffices. Owner passes everything via the system role; token-holder operations (`/auth/*`) are exempt. Existing integrations using an employee-level token for admin reads will now receive `403 {"code": "FORBIDDEN"}` and need a token from a user whose role grants the corresponding permission. Bundle API endpoints (timeoff, swaps, timeclock, shift claims, messages, feedbacks, daily reports) are not mapped yet and keep token-only auth for now.
- **Breaking (API)**: `/api/v1/notifications*` is now strictly personal: every endpoint operates on the token holder's notifications only. The `?user_id=` parameter that allowed reading, marking as read, or mass-marking **another user's** notifications is gone (it's ignored), and fetching/deleting someone else's notification by id now returns 404 instead of leaking or destroying it.

### Added
- The RBAC permission system now covers the optional bundles too — until now, their admin pages only required "manages at least one store" and their API endpoints only required a valid token. Five new permission categories in `PermissionCatalog` (`timeoff` view/create/update/approve/delete, `swaps` view/create/update/approve/delete, `timeclock` view/update/delete, `open_shifts` view/publish/approve, `feedbacks` view/update/delete), and the report-style bundles reuse existing categories (HiringReport/ResignationReport/StorePhoto → `documents.*`, SalaryReport → `payroll.*`, reactivating a resigned user → `employees.update`). `PermissionMiddleware` was added to the admin route groups of TimeOff, ShiftSwap, Timeclock, ShiftClaim, Feedback, HiringReport, ResignationReport, SalaryReport and StorePhoto with the matching `config/permissions.php` entries, and `ApiPermissionMiddleware` to the API groups of TimeOff, ShiftSwap, Timeclock, ShiftClaim and Feedback with the matching `config/api-permissions.php` rules. The API "self" rule now also reads the targeted `user_id` from the request body (POST/JSON), so an employee token can still clock **itself** in/out, list its own time-off requests or claims, and submit its own feedback without any permission — while doing any of that for someone else now requires the mapped key (previously any token could clock in/out **any** employee). A data migration (`2026_07_14_000005`) grants the new keys to every existing role holding `shifts.update` (manager-like roles), so current managers keep their access; `MANAGER_DEFAULTS` includes them for fresh installs. The manager sidebar now hides the Timeclock/Time-off/Swaps/Open-shifts/Reports/Photos links a user's roles don't grant. DailyReport keeps its own store-configurable permission system (its RBAC migration is tracked separately) and Messaging stays self-service (participant-scoped in its controllers). Docs updated (wiki API Reference & Security Overview, en/fr/ja).
- The role form (`/admin/roles`) is now bundle-aware: permission categories carried by a disabled bundle are hidden from the matrix (their routes don't exist anyway), driven by a new `PermissionCatalog::CATEGORY_BUNDLES` map. Grants already saved for a hidden category survive an edit round-trip (the controller merges them back on save) and reappear when the bundle is re-enabled.
- The RBAC permission matrix now actually gates the admin web pages, instead of any managing role granting full manager access: a new `PermissionMiddleware` (added to the `/admin` route group after `AdminMiddleware`) reads the required permission for the matched route from a new declarative `config/permissions.php` map (route name → `PermissionCatalog` key, covering the employees/stores/shifts/shift-types/payroll-stats domains) and rejects the request with a 403 when none of the user's roles grants it. When the permission is granted per-store, `managed_store_ids` is narrowed to the stores where **that specific permission** is held (not just "any permission"), so every controller's existing store filtering automatically scopes data per permission — e.g. a role with `shifts.view` on store A and `employees.view` on store B sees only store A's planning and only store B's staff. Owner (system role) bypasses all checks, routes absent from the map keep the previous coarse behavior (bundle admin pages will be mapped separately), and the default Manager role holds every mapped key so existing managers notice no change. The sidebar now hides the Staff/Stores/Planning/Reports links a user's roles don't grant (`user_can` view helper shared by the middleware), and the matched route's name is now attached to the request (`route_name` attribute) by `Application::dispatch()`.

### Changed
- The hardcoded store-role selectors (`staff`/`manager`/`admin` — the confusing "Store Administrator" among them) are gone from the UI: the "add member" and "change role" forms on `/admin/stores/{id}/edit`, the "assign to store" forms on the user create/edit pages, and the shift-import quick-create modal now list the dynamic roles from the `roles` table (anything the Owner created at `/admin/roles`, minus system roles like Owner which are global-scope only) and post a `role_id` instead of a legacy role string. Picking a role both writes the matching `role_assignments` row (via new `RoleAssignmentSyncService::syncStoreRoleById()`) and derives a transitional value for the legacy `store_user.role` column (`manager` if the role grants at least one permission, `staff` otherwise) so legacy readers (`DailyReportPermissionService`, payslip/report views) keep working until that column is dropped in the cleanup phase. Member lists now display the actual assigned role name instead of the fixed three labels, and the last hardcoded role vocabularies (`AdminStoreController::ROLES`, `StoreService`-driven `$roles` maps in `users-form.php`/`stores-form.php`/`_form-user.php`/`users.php`) were removed; the legacy string-based `RoleAssignmentSyncService::syncStoreRole()` is gone too, replaced by the id-based variant. Custom roles created by the Owner are now genuinely assignable to users, per store, from the existing membership forms.

### Fixed
- Creating an employee with an email address that already belongs to another account (standard "new user" form, quick-create from the shift-import preview, or editing an existing user's email) crashed with an uncaught SQL unique-constraint exception instead of a clear error — most visible when an import's name-matching didn't recognize an employee who already existed under a different Excel name, so the same real email got submitted twice via quick-create. `AdminUserController::storeUser()`/`updateUser()`/`quickCreateUser()` now check email uniqueness upfront (same pattern already used for `employee_code`) and return a clear `email_taken` error instead of crashing.

## [0.7.0] - 2026-07-14

### Added
- Maintenance mode: Owners can now block access to the site's web pages for everyone except themselves, either manually (new toggle + optional custom message on `/admin/owner-settings`, stored as `maintenance_mode_enabled`/`maintenance_message` app settings) or automatically for the duration of a self-update or a pending-migrations run (`BackupController::update()`/`updateStream()`/`migrate()` now enable it beforehand and restore its previous state afterwards, even on failure). Implemented as a new global `MaintenanceModeMiddleware` (positioned right after `AppSettingsMiddleware` in `config/middleware.php`) that throws a new `ServiceUnavailableException` (503, rendered by a new `errors/503.php` view) for any anonymous or non-owner request outside `/login`; `/api/*` and `/cron/*` stay reachable throughout so external integrations (cron-job.org, UptimeRobot, mobile/API clients) aren't affected by the maintenance window. Fails open (never blocks the site) if `app_settings` can't be read, e.g. before that table exists.
- Foundations for a dynamic RBAC (role-based access control) system: new `roles`, `role_permissions`, and `role_assignments` tables, seeded at migration time with three default roles (Owner/Manager/Employé) replacing the hardcoded `users.is_admin` flag and `store_user.role` string in the long run. A user can hold several role assignments, each scoped either globally (`scope_type='global'`, e.g. Owner) or to a specific store (`scope_type='store'`), which natively supports assigning the same role across multiple stores (e.g. an "Area Manager"). New `PermissionCatalog` (`src/Core/Auth/PermissionCatalog.php`) defines the available permission keys grouped by category (employees/shifts/stores/payroll/documents/settings), and a new `PermissionService::can()`/`scopedStoreIds()` (`src/Core/Auth/PermissionService.php`) resolves them against a user's role assignments, short-circuiting to `true` for system roles (Owner) regardless of the `role_permissions` table. This is purely additive: nothing in the application reads from these new tables yet — `AuthService`/`HasAdminAccess` still drive authorization from `is_admin`/`store_user.role` as before. First phase of a broader RBAC migration (see `task/mermission.md`); no user-visible behavior change.
- `scripts/migrate-roles.php`, second phase of the RBAC migration: backfills `role_assignments` from the existing `users.is_admin`/`store_user.role` data (the legacy per-store `admin` role — the confusing "Store Administrator" — is merged into `Manager`, since it has always carried identical permissions in the code). Idempotent (safe to re-run, already-existing assignments are skipped) and read-only towards the legacy columns (`is_admin`/`store_user.role` are left untouched, still authoritative until the Phase 3 cutover). `--dry-run` prints a per-user comparison between the current `is_admin`/`managedStoreIds()`-equivalent computation and what it will become once role assignments drive authorization, as a safety net before applying.
- Owner-only role management UI at `/admin/roles` (new "Rôles" settings tab), third phase of the RBAC migration: create, rename, recolor, describe, and delete custom roles, grant/revoke permissions through a checkbox matrix grouped by `PermissionCatalog` category, and see which users currently hold a given role (`AdminRoleController`, `system/roles.php`, `system/roles-form.php`). The system Owner role is read-only here (not renamable, not deletable, no permission matrix — it always has every permission) and a role still assigned to at least one user can't be deleted until it's been removed from everyone first. Still purely additive: creating or editing a role here has no effect yet on what anyone can actually do — `AuthService` doesn't read `role_assignments` until the Phase 3 cutover.
- RBAC cutover: `AuthService::isAdmin()`/`managedStoreIds()`/`isManager()` now compute from `role_assignments` instead of `users.is_admin`/`store_user.role` — the change is isolated to `AuthService::user()`, which overlays the effective `is_admin` value onto the returned user array, so every existing controller/view that reads `$request->getAttribute('auth_user')['is_admin']` (Owner-only gates in `BackupController`, `BundleSettingsController`, `OwnerSettingsController`, `LanguageController`, `AdminController`, `EmployeeController`, `DailyReportPermissionService`, ...) keeps working unchanged. A new migration (`2026_07_14_000004_backfill_role_assignments`) runs the same backfill as `scripts/migrate-roles.php` automatically on every deploy/self-update, so existing instances never end up with `AuthService` reading an empty `role_assignments` table. A new `RoleAssignmentSyncService` keeps `role_assignments` in sync going forward: creating/editing a user's Owner flag (`AdminUserController::storeUser()`/`updateUser()`/`quickCreateUser()`) and adding/changing/removing a store membership (`AdminStoreController::addMember()`/`updateMemberRole()`/`removeMember()`) now also write the corresponding role assignment, not just the legacy columns. The installer (`public/install.php`) assigns the Owner role to the account it creates for the same reason. `DailyReportPermissionService` and the API needed no changes — the former only reads `store_user.role` directly (untouched) and the bridged `is_admin`, the latter still has no authorization layer (tracked separately).

## [0.6.0] - 2026-07-10

### Added
- Owners can now clone or refresh the local wiki (`.wiki/`) directly from `/docs`, instead of having to `git clone` it on the server by hand: a new `WikiSyncService` fetches every page listed in the wiki's `_Sidebar.md` (for all 3 languages) straight from `raw.githubusercontent.com/wiki/{repo}/...` over plain HTTPS — no `git` binary or `exec()` needed, same shared-hosting-friendly approach as `GithubUpdateService`'s self-update mechanism. A single idempotent `sync()` call handles both cases: it clones everything on first run (nothing local yet) and only rewrites pages whose content actually changed on subsequent runs, skipping unchanged ones and treating a missing translation (HTTP 404) as normal rather than an error. Exposed as `POST /docs/sync` (`DocsController::sync()`, owner-only, mirroring the `requireOwner()` pattern used by `BackupController`/`LanguageController`), with a "Clone the wiki" / "Update the wiki" button shown on `/docs` for owners, reporting added/updated/unchanged counts. Needed an explicit `WikiSyncService` singleton binding in `AppServiceProvider`, since its constructor takes a nullable `\Closure` (test-only fetcher override) that the container's reflection-based auto-resolution cannot instantiate on its own — same reason `GithubUpdateService` already required one.
- The documentation page (`/docs`) now renders the GitHub wiki directly in the app: a new route `GET /docs/{lang}/{page}` (`DocsController::show()`) renders each wiki page as HTML via a new `WikiContentService`, reading from a local `.wiki/` clone (gitignored, populated separately from the actual GitHub wiki repo). It matches the wiki's real structure — English pages at the root, `fr/`/`ja/` subfolders for translations, navigation driven by parsing the wiki's own `_Sidebar.md` — rather than assuming a fixed file list. The reader view groups the sidebar table of contents by the sidebar's own sections, adds prev/next pagination and a language switcher (shown when the current page has a translation), and localizes each page's title from its first `#` heading. Internal wiki links (GitHub's relative-path convention, e.g. `Installation`, `../Home`, `../ja/Home`) are resolved and rewritten to in-app routes — with slug validation against path traversal — external links are left untouched, and unresolvable internal links degrade to plain text. Each language card on `/docs` links straight into the wiki's home page when it actually exists on disk for that language, and always shows a "View on GitHub" link to the live wiki regardless of whether `.wiki/` is cloned locally — same on the reader page (header link for the current page, and per-item links in the sidebar for pages not available in the current language). GitHub URLs are built from the `GITHUB_UPDATE_REPO` env var already used for self-update checks (`WikiContentService::githubWikiUrl()`), so no local file access is needed to produce them. This replaces the previous PDF-based guide system (`WikiPdfGeneratorService`, `WikiPdfController`, `scripts/pdf.php`, the committed `public/pdf/*.pdf` files, and the `/api/v1/pdf/generate` endpoint), which has been removed entirely.
- Update channel selector on `/admin/update` (Alpha / Beta / Release), stored as the `update_channel` app setting (`AppSettingsService::updateChannel()`). `GithubUpdateService::checkLatestRelease()` now lists all GitHub Releases (`GET /repos/{repo}/releases`) instead of only the latest stable one, and picks the highest version compatible with the configured channel: `release` only considers stable tags, `beta` also considers `-beta` tags, and `alpha` considers everything (alpha/beta/stable) — laying the groundwork for the `alpha`/`beta` release branches and their automated GitHub Actions publishing.

### Fixed
- `/admin/update` crashed with a `TypeError` whenever GitHub's API returned an error response (e.g. rate limit exceeded) instead of the expected list of releases. `GithubUpdateService::fetchReleaseListData()` only checked `is_array()` after `json_decode()`, but GitHub's JSON error objects (`{"message": "API rate limit exceeded..."}`) decode to a PHP array too, so they were passed straight into `selectReleaseForChannel()`'s `array_filter()` as if they were releases, crashing on the first non-array value. Now requires the decoded response to be a list (`array_is_list()`) before accepting it as a release list, otherwise treats it the same as any other failed fetch (returns `null`, `checkLatestRelease()` reports no update available instead of crashing the page).
- Employees created from the shift-import quick-create modal (`POST /admin/users/quick-create`) were silently never attached to the target store. `_partials/_form-user.php` always renders a `<select name="store_id">` in `create` mode, but the import preview's `qc-form` (`scheduling/shifts-import-preview.php`) already carries the real store as a `<input type="hidden" name="store_id">` set by the caller; since the partial's own select had no options in that context (`$all_stores` is intentionally empty there), the two same-named fields collided and the empty `<select>` — submitted after the hidden input in DOM order — silently overwrote it, so `AdminUserController::quickCreateUser()` always received `store_id=0` and skipped both `assertStoreAccess()` and the `store_user`/hiring-report creation with no error surfaced. This made the new employee invisible to any Manager (whose "Personnel" list is filtered by store membership) while still visible to an Owner (unfiltered list), which could look like a Manager-only permission bug. The store `<select>` in the partial is now only rendered when `$all_stores` is non-empty, leaving the quick-create modal's hidden field as the sole `store_id` source.

### Changed
- Removed the `/docs` language-selection grid: now that the wiki can be browsed directly in the app, picking a language card added a step without adding value. `GET /docs` now goes straight to the wiki's home page in the user's current locale (`DocsController::index()` redirects to `docs.show` as soon as that page exists in `.wiki/`) instead of showing a "browse online" button per language. If the current locale isn't cached locally, `/docs` renders a message saying so, with a "View on GitHub" link (works with no `.wiki/` clone at all) and, for owners, a "Clone the wiki" button right there to fetch it on the spot. The wiki reader page (`docs/show.php`) also gained its own owner-only "Update the wiki" button in the header, so refreshing content no longer requires going back to a hub page first — it now works from wherever you're reading.
- Release publishing is now automated: `.github/workflows/release.yml` tags and publishes a GitHub Release whenever a version bump is merged into the `alpha`, `beta`, or `main` branch — `alpha`/`beta` get an auto-incremented prerelease suffix (`vX.Y.Z-{channel}.N`), `main` publishes the plain stable tag (skipped if it already exists). The base version bump in `composer.json`/`config/app.php`/`CHANGELOG.md` is still done by hand as before; only the tag/`gh release create` step is now automatic. `alpha`, `beta`, and `main` are protected branches (PR + passing CI required). See `docs/releasing.md` for the updated flow.

### Fixed
- The Daily Report list tables (`/admin/stores/{id}/daily-reports` and its "all reports" view) had the Sales/Labor Cost column headers hardcoded in Japanese (`売上`, `人件費`) instead of going through the translation system. Fixed to use the existing `dr_sales`/`dr_labor` keys, already used everywhere else in these same views (row cells, PDF, email) — no new translation keys needed.

## [0.5.0] - 2026-07-09

### Added
- New Owner settings tab, **Bundles** (`/admin/bundles`), to enable/disable each installed bundle for the whole instance — previously only possible by hand-editing `config/license.php`. The toggle is stored in `app_settings` (`enabled_bundles`) via `LicenseServiceProvider`, which now reads that setting first and falls back to `config/license.php` when unset (so existing deployments keep working unchanged). The per-store feature toggle (store edit page) now also lists `photos` and only proposes bundle-backed features (`messages`, `daily_reports`, `photos`) when the corresponding bundle is enabled instance-wide; `StorePhotoController` now actually enforces the per-store `photos` toggle (it previously had no such check, unlike the employee-facing time off/swap/open-shift/messaging flows).
- Bundles are no longer hardcoded in a registry: `BundleDiscoveryService` scans `src/Bundles/*/` at boot and auto-detects any `{Name}\{Name}Bundle` class extending `Bundle`, replacing the removed `config/bundles.php`. Third-party bundles just need to be dropped in `src/Bundles/` (same PSR-4 convention) to show up on `/admin/bundles` — no core code change needed. A new `config/official-bundles.php` lists the slugs of bundles actually developed and maintained by the Kintai project; anything discovered but absent from that list is flagged "third-party" on `/admin/bundles` with a warning that it isn't maintained by the main project. `Bundle` gained optional `getLabel()`/`getDescription()` methods for this listing (overridden by `DailyReportBundle`/`MessagingBundle`, default to a humanized slug otherwise). `config/official-bundles.php` was also missing `store-photos` since its own extraction; fixed here.
- Time off management (employee submission, admin approve/refuse/create-on-behalf, `/api/v1/timeoff-requests`) moved into a new `timeoff` bundle (`src/Bundles/TimeOff/`). Unlike other bundles, `TimeoffRequestRepositoryInterface` stays registered in Core (`RepositoryServiceProvider`) rather than moving into the bundle: `StoreStatsService`, `ShiftService`, `AdminShiftController`, `IcalController`, and `EmployeeController`'s dashboard all read time-off data for calculations that must keep working even when this bundle is disabled — only the dedicated management UI and its routes are bundle-only. `EmployeeController`'s `assertFeature()` store-level feature check was extracted into a reusable `HasStoreFeatureCheck` trait, shared with the bundle's new `EmployeeTimeoffController`. Enabled by default, so no behavior change for existing deployments.
- Translations are no longer all centralized in `lang/*.json`: a bundle can now ship its own `src/Bundles/<Name>/lang/{fr,en,ja}.json`, so bundle developers no longer have to touch Core's translation files to add or edit strings for their own feature. `JsonTranslationRepository` merges the Core files with every bundle's `lang/` directory found on disk (regardless of whether the bundle is currently enabled, so its strings stay available if it's re-enabled later); a bundle only needs to define the keys it actually uses — anything it doesn't redefine falls back transparently to the Core value, and a bundle can also override a Core key for its own context. Editing an existing bundle-owned string from the Owner "Languages" admin page (`/admin/languages`) now writes back to that bundle's file instead of re-centralizing it into Core. All ~300 translation keys that were already exclusive to one of the 11 existing bundles (e.g. `dr_*` for Daily Report, `sr_*` for Salary Report, `feedback_*`, `bundle_daily_report`/`_desc`, ...) were moved out of `lang/*.json` into their owning bundle's own files, in all three languages.
- Wired up the orphaned `backup` cron job: `CronRunner`, `AutoValidateJob`, and `BackupJob` were fully implemented but never registered or reachable from any route. `AppServiceProvider` now builds a `CronRunner` singleton with both jobs registered, and a new `GET /cron/run/{job}` route (token-scoped via the `cron_tokens` table, `Authorization: Bearer` or `?token=`) exposes them. `scripts/create-cron-token.php` issues the per-job tokens this endpoint needs.

### Changed
- Store photos (weekly store-condition photo submissions, retention/cleanup settings) moved out of Core into a new `store-photos` bundle (`src/Bundles/StorePhoto/`), following the same pattern as the Messaging and Daily Report bundles. `StorePhotoController`, its routes, and its views moved under the bundle; `StorePhotoRepositoryInterface` is now registered by the bundle instead of the core `RepositoryServiceProvider`. Enabled by default (`config/license.php`), so there is no behavior change unless a deployment explicitly disables it. First step of the broader effort to shrink Core down to Shift/User/Store and move every optional feature (time off, shift swaps, open shifts, HR reports, ...) into its own toggleable bundle.
- Shift swap management (employee propose/accept/refuse/cancel, admin apply-immediately/approve/refuse, `/api/v1/shift-swap-requests`) moved into a new `shift-swap` bundle (`src/Bundles/ShiftSwap/`). Like `timeoff`, `ShiftSwapRequestRepositoryInterface` stays registered in Core (`RepositoryServiceProvider`) instead of moving into the bundle: `StoreStatsService`, `HomeController`, and `EmployeeController`'s dashboard all read swap data for calculations that must keep working even when this bundle is disabled — only the dedicated management UI and its routes are bundle-only. `EmployeeController`'s two swap-only helpers (`buildUsersMap()`/`buildShiftsMap()`) moved into the bundle's new `EmployeeSwapController` along with the swap methods, reusing the `HasStoreFeatureCheck` trait. Enabled by default, so no behavior change for existing deployments. Also fixes `config/official-bundles.php`, which was still missing `store-photos`.
- Open shifts / shift claims (publish a shift to the bourse, employee claim/withdraw, admin approve/reject, `/api/v1/shift-claims`) moved into a new `shift-claim` bundle (`src/Bundles/ShiftClaim/`). Unlike `timeoff`/`shift-swap`, no Core component reads shift-claim data directly, so `ShiftClaimRepositoryInterface` moved into the bundle itself (like `store-photos`) instead of staying a Core service — disabling the bundle removes the feature entirely. This required splitting six methods (`openShifts`, `selectShiftToPublish`, `publishShift`, `unpublishShift`, `approveShiftClaim`, `rejectShiftClaim`) out of `AdminShiftController`, the Core scheduling controller that also handles plain shift CRUD, and three methods out of `EmployeeController`. Enabled by default, so no behavior change for existing deployments. Also fixes `config/official-bundles.php`, which was still missing `store-photos`.
- Resignation, salary, and hiring reports moved into new `resignation-report`, `salary-report`, and `hiring-report` bundles (`src/Bundles/ResignationReport/`, `src/Bundles/SalaryReport/`, `src/Bundles/HiringReport/`). `AdminReportController` (Core) previously handled all three report types through a single `repo(string $type)` dispatch and ~300 lines of CRUD/PDF logic shared across them; that controller is now retired entirely, replaced by three bundle controllers (`AdminResignationReportController`, `AdminSalaryReportController`, `AdminHiringReportController`) sharing the CRUD/PDF logic via a reusable `HasStaffReportCrud` trait. `ResignationReportRepositoryInterface` and `SalaryReportRepositoryInterface` move into their respective bundles (like `store-photos`, no other Core component reads that data). The salary bundle's `calculateSalaryPreset()` depends on `DailyReportRepositoryInterface` (the DailyReport bundle) to pre-fill the month's sales total from validated/submitted daily reports — a bundle-to-bundle dependency, so salary-report creation assumes daily-report stays enabled. Unlike resignation/salary, `HiringReportRepositoryInterface` stays a Core service instead of moving into its bundle: `AdminUserController` reads/writes it directly to auto-generate a hiring report on every employee creation (standard form and Excel quick-create), a Core user-management workflow that must keep working even when the hiring-report bundle is disabled — disabling it removes only the browse/edit/PDF UI, not that auto-generation or the underlying data. Enabled by default, so no behavior change for existing deployments. Also fixes `config/official-bundles.php`, which was still missing `store-photos`.
- Employee feedback (submission modal, admin list/delete, `/api/v1/feedbacks`) moved out of Core into a new `feedback` bundle (`src/Bundles/Feedback/`). Both the Web (`Requests\FeedbackController`) and API (`Api\V1\FeedbackController`) controllers moved under the bundle; `FeedbackRepositoryInterface` is now registered by the bundle instead of the core `RepositoryServiceProvider` (no other Core component reads feedback data). One wrinkle unlike other full extractions: the feedback submission modal is included directly by the shared `app.php` layout on every employee page, not routed through the bundle's own views — `AuthMiddleware` now shares a `feedback_enabled` flag (from `FeatureManager`) that the layout checks before including it, so the modal (and its now-404 POST target) disappears cleanly when the bundle is disabled instead of silently breaking. Enabled by default, so no behavior change for existing deployments. Also fixes `config/official-bundles.php`, which was still missing `store-photos`.
- Clock-in/out moved into a new `timeclock` bundle (`src/Bundles/Timeclock/`): the employee clock-in/out page, admin timeclock entries list/edit/delete, and `/api/v1/timeclocks` all moved under the bundle. Like Time Off/Shift Swap, `TimeclockRepositoryInterface` stays a Core service instead of moving into the bundle — `HomeController`'s admin dashboard widget and `EmployeeController::dashboard()`'s employee widget both read it for "who's clocked in right now" calculations that must keep working even when the bundle is disabled. `EmployeeController`'s `assertFeature()` store-level feature check was extracted into a reusable `HasStoreFeatureCheck` trait, shared with the bundle's new `EmployeeTimeclockController` (previously duplicated per controller). The existing per-store `timeclock` feature toggle (store edit page) now also gates on this bundle via `AdminStoreController::FEATURE_BUNDLE_MAP`, same as `messages`/`daily_reports`/`photos`. Enabled by default, so no behavior change for existing deployments. Also fixes `config/official-bundles.php`, which was still missing `store-photos`.
- Moved all translated documents (`*.fr.md`, `*.ja.md`) into `docs/i18n/`, including the ones formerly living next to their English source in `docs/`. `docs/security.md` was renamed to `docs/security-overview.md` to avoid a case-insensitive filename clash with the root `SECURITY.md` translations. `scripts/check-translations.php` now always looks for translations under `docs/i18n/` regardless of the source document's folder.
- `docs/database.md` updated to reflect the actual `illuminate/database` version (^13.19, not ^11.0) and clarified that the `Language`/`Translation` repository interfaces are now bound to JSON-file-backed implementations, not Eloquent — their `Database*Repository` counterparts are unused dead code left over from before the i18n JSON migration.
- Split the combined "Backups & Updates" settings tab into two separate tabs, **Backups** and **Updates**. The GitHub self-update UI (version, pending migrations, one-click update with progress) now lives on its own page at `/admin/update`, while `/admin/backup` only handles create/restore/delete. ### Fixed
- The installer no longer fails with "Database file at path [...] does not exist." when `storage/app/database.sqlite` is missing (e.g. after an incomplete or deleted previous install) — the file and its directory are now created automatically before the framework boots.
- `docs/releasing.md` (and its FR/JA translations) still pointed to `/admin/backup` for the self-update UI; fixed to `/admin/update`, matching the settings-tab split.
- **Security:** the Messaging and DailyReport bundles' `/api/v1/*` routes were registered without `ApiAuthMiddleware`, unlike every other `/api/v1/*` endpoint — they were reachable without a Bearer token even though their controllers assumed an authenticated `auth_user`. Both bundles' `routes.php` now wrap their API routes in the same protected group as the core API.
- **Critical:** shift swap requests were completely broken — creating, accepting, or refusing a swap wrote/read the columns `target_id`/`peer_accepted_at`, which don't exist in the `shift_swap_requests` table (real columns: `target_user_id`/`accepted_at`). Every attempt to create a swap threw a SQL error, and swap statistics silently under-counted the target side. Fixed in `EmployeeController`, `AdminSwapController`, the swap views, the dashboard, and `StoreStatsService`.
- `DELETE /api/v1/notifications/{id}` marked the notification as read instead of deleting it. `NotificationRepositoryInterface` gained a `delete()` method and the endpoint now actually deletes.
- `scripts/db-migrate.php --dry-run` was documented but never implemented — the script read no CLI arguments at all. It now lists pending migrations without applying them.
- `scripts/docker-setup.php` hashed the admin password with a different bcrypt cost than `install.php`/`provision.php`; aligned to cost 12.
- `.env.example` was missing several variables actually read via `env()` elsewhere (`DB_PREFIX`, `DB_CHARSET`, `DB_COLLATION`, `DB_DRIVER`, `SESSION_NAME`, `SESSION_LIFETIME`, `SESSION_SECURE`, `SESSION_HTTPONLY`, `SESSION_SAMESITE`, `APP_NAME`, `APP_VERSION`); added with their real defaults.
- **Critical:** disabling a bundle from `/admin/bundles` crashed the dashboard and sidebar with a 500 ("Route [...] not defined") for every user whose store still had the corresponding `store_features` slug checked (and unconditionally for Owner accounts, since the per-store toggle is bypassed for them). The sidebar, bottom nav, and both dashboards generated `route_url()` links to bundle-owned routes based only on the per-store toggle, never on whether the bundle itself was still enabled instance-wide. Added `FeatureManager::STORE_FEATURE_BUNDLE_MAP` (single source of truth for the store-feature-slug → bundle-slug mapping, replacing `AdminStoreController`'s private copy) plus two helpers, `bundle_enabled()`/`feat_bundle()`, now consulted everywhere a bundle-gated route is linked: the three independent `$feat()` closures (`app.php`, `dashboard/index.php`, `employee/dashboard.php`), the Owner/Manager branches of `_sidebar.php` (the Owner branch previously had no bundle check at all), `_bottomnav.php` (hrefs are now lazy closures, since the nav-item pool array previously called `route_url()` unconditionally for every item before the per-item visibility filter ran), the "feedbacks" settings tab, and the "request a swap" button on the three shift-calendar/timeline views.
