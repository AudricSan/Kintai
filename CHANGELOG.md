## [Unreleased]

### Fixed
- Several RBAC gaps allowed a non-Owner role to see (and sometimes actually reach) functionality beyond its granted permissions, or to fail silently on save after filling a form it should never have been shown: (1) the legacy `store_user.role` column, never resynced when an Owner edits a role's permissions after assignment, still drove the shift-management button on the employee planning page and the manager picker in HR report forms — both now consult `PermissionService` directly; (2) `/admin/activity` had no permission entry and no store scoping, so any single-store manager could read the whole organization's audit log — now requires `stores.view` and is filtered to the manager's stores; (3) `staff/users.php`, `staff/stores.php`, `staff/stores-form.php` and `staff/users-form.php` rendered links/forms toward actions gated by a stricter permission than the page itself (e.g. the user edit page only needs `employees.view`, but saving needs `employees.update`) without ever checking `$can()` — the edit form now goes read-only with a notice instead of accepting input it can't submit; (4) the DailyReport bundle (web and API) had no declarative permission mapping at all, and its API controller never checked authorization — any token holder could view/edit/delete any store's daily report. Added a new "permission OR store membership" rule to `PermissionMiddleware`/`ApiPermissionMiddleware` so the bundle's self-service model (any store member can manage their own report) is now expressed declaratively instead of being implicit, and wired the missing `DailyReportPermissionService` checks into the API controller.

## [0.8.0] - 2026-07-17

### Changed
- `alpha`/`beta` releases now use a rolling tag (`vX.Y.Z-{channel}`, deleted and recreated on each push) instead of an ever-incrementing `vX.Y.Z-{channel}.N` — the old scheme had reached `.16` for a single version and helped bury the actual latest stable release under a long tail of prereleases. The `Release` workflow now also refuses to publish an alpha/beta prerelease once `vX.Y.Z` (no suffix) already shipped as a stable Release, since a same-numbered prerelease would be semver-lower than the stable tag and therefore invisible to that update channel — bump the base version first instead.
- Documented the MINOR vs. PATCH convention in `docs/releasing.md`: any release bundling a new feature or behavior change bumps MINOR (even if fixes ride along in the same release), PATCH is reserved for bugfix-only releases. Prompted by `main` sitting at `0.6.0` while `beta` had raced to `0.7.9` through nine consecutive PATCH bumps that actually contained feature work — understating how far the stable channel had drifted.

### Fixed
- `GithubUpdateService::fetchReleaseListData()` only requested the first page (30 items) of `GET /repos/{repo}/releases`, which the GitHub API returns newest-first — once a repo accumulates more than 30 releases (alpha/beta included, each a distinct GitHub Release under this project's channel workflow), the last stable release can be pushed past that page entirely. On the "release" channel this meant the instance update page silently showed "No GitHub release available" instead of comparing against the actual latest stable release. Now paginates (100 per page, up to 5 pages) and stops as soon as a release compatible with the configured channel is found among the pages fetched so far.
- Deleting a resignation report left the linked employee deactivated: `storeResignationReport()` sets `is_active = 0` on creation, and the explicit "Reactivate" action already reverses that, but deleting the report itself did not — so removing the report (e.g. created by mistake) permanently stranded the employee as inactive with no report left to reactivate from. `deleteResignationReport()` now reactivates the linked user first, same as the explicit reactivate action, before deleting the report.
- The navigation settings page (`/admin/nav-settings`) had no toggle to hide/show the hiring, resignation or salary report links — `$allSections['statistics']` (which drives the checkbox list) only listed `employee_report`/`daily_reports`/`photos`, even though the sidebar itself already supports hiding all three (`$navHide('hiring_report')`/`'resignation_report'`/`'salary_report'`). Added the missing entries (for both Owner and Manager, gated by the same `bundle_enabled()` check the sidebar uses, so a disabled report bundle doesn't show a dead toggle).
- Renamed the "Photos" nav link/page title (`photos_report`) to "Photo Report" (`Rapport photographique` / `写真報告書`) to match the naming pattern of the other reports in the same menu section ("Salary Report", "Resignation Report", "Hiring Report"). Split off a new `photos_count` key ("Photos") for the two places that were actually counting photos (upload preview, submission card badge — `photos_report` there would have read as "3 Photo Report").

## [0.7.7] - 2026-07-17

### Fixed
- The GitHub update check (`/admin/update`) relied exclusively on `@file_get_contents()` over PHP's URL stream wrapper, with every network/SSL/DNS error and every GitHub API error response (rate limit, auth, 404...) silently swallowed into a bare `null` — the page then showed the exact same "no update available" message whether the instance was genuinely up to date or the check had failed outright, with nothing written to any log. This made the failure undiagnosable on hosts like OVH shared hosting where `allow_url_fopen` can be disabled or outbound requests to `api.github.com` restricted/rate-limited on a shared IP. `GithubUpdateService` now prefers curl (typically available even when `allow_url_fopen` is off) with a stream-wrapper fallback, for both the release-list check and the update zip download; any failure is logged (`Log::warning`, visible in the activity log) with the actual reason (curl error, HTTP status, PHP stream error, or the raw GitHub API error message) and exposed via a new `getLastCheckError()`. The update page now shows a distinct warning with that reason instead of the generic "no release available" message when the check itself failed, while still showing the plain "no release yet" message when the check succeeded but no release matches the selected channel (not an error).
- The store edit form's "auto pause" fields (`auto_pause_after_minutes`, `auto_pause_minutes`, under "Shift settings") appeared to never save: `updateStore()` correctly persists them to the `store_import_settings` table via `saveImportSettings()`, but the edit form re-read them from `stores.excel_import_settings`, a legacy JSON column nothing writes to anymore — so the form always displayed stale/default values regardless of what was actually saved. `_form-store.php` now reads these fields from `$importSettings` (`StoreRepositoryInterface::getImportSettings()`, already fetched by `AdminStoreController::editStore()` but previously unused), matching the source the real Excel-import path (`AdminShiftImportController`) already relies on. Also removed a duplicate, dead copy of the same buggy lookup in `stores-form.php`.

## [0.7.6] - 2026-07-16

### Fixed
- Full (factory) reset (`/admin/backup` danger zone) followed by reinstalling through the web installer used to leave the `roles` table permanently empty: the seed migration that creates Owner/Manager/Employé guards itself against re-inserting duplicates, but since `resetFactory()` wipes every table's data except `migrations`, the migration stayed marked as already-applied and its guard silently blocked any reseed forever. Migrations can now mark themselves as a seed (`Migration::isSeed()`) instead of `AppResetService` hardcoding migration names — `MigrationRunner::getSeedMigrationNames()` exposes them, and `resetFactory()` untracks them (before wiping the tables, not after, so an interruption in between can't reproduce the same data loss) so they replay and reseed on the next install.

## [0.7.5] - 2026-07-15

### Security
- **Breaking (API)**: `/api/v1/*` now enforces RBAC authorization — until now, any authenticated token (including a plain employee's) could read and modify every resource of every store. A new `ApiPermissionMiddleware` (after `ApiAuthMiddleware` on the `/api/v1` group) checks each route against a declarative `config/api-permissions.php` map (route name → `PermissionCatalog` key, with an optional "self" rule letting users access their own sub-resources — own profile, own prefs/rates/iCal tokens — without any permission). When the request targets a store (`store_id` route param, query param, or body field), the permission must be granted **for that store** (or through a global-scope role); otherwise holding it anywhere suffices. Owner passes everything via the system role; token-holder operations (`/auth/*`) are exempt. Existing integrations using an employee-level token for admin reads will now receive `403 {"code": "FORBIDDEN"}` and need a token from a user whose role grants the corresponding permission. Bundle API endpoints (timeoff, swaps, timeclock, shift claims, messages, feedbacks, daily reports) are not mapped yet and keep token-only auth for now.
- **Breaking (API)**: `/api/v1/notifications*` is now strictly personal: every endpoint operates on the token holder's notifications only. The `?user_id=` parameter that allowed reading, marking as read, or mass-marking **another user's** notifications is gone (it's ignored), and fetching/deleting someone else's notification by id now returns 404 instead of leaking or destroying it.

### Added
- The employee search field on `/admin/users` now matches regardless of the script you type in and filters instantly with zero server round-trip (no page reload while typing, unlike every other filter — see the "Filter bars apply instantly" change below): an employee whose name is stored in kanji (e.g. 山田太郎) is found by typing its romaji reading ("yamada"), hiragana (やまだ), or katakana (ヤマダ), not just the kanji itself. Each row carries the searchable text and furigana reading as data attributes (`data-search-text`/`data-search-reading`, set from `furigana_last_name`/`furigana_first_name` — already collected on the user form, previously only used for PDF/report display); a new `kana-search.js` module (a JS port of the matching algorithm, kept in sync with the PHP `KanaSearch` service used elsewhere/tested in `KanaSearchTest`) converts a romaji query to katakana (Hepburn table, handling sokuon/youon/moraic ん) and normalizes hiragana/katakana input, entirely client-side. Falls back to plain substring matching on name/employee code/email when no reading is available — which, today, is most employees, since furigana is an optional field nobody has been filling in; the reading-based match only helps once it's populated. To lower that barrier, the user create/edit form (and the shift-import quick-create modal, same shared partial) now auto-suggests `furigana_last_name` from a ~160-entry dictionary of common Japanese surnames (new `furigana-suggest.js`) as soon as `last_name` loses focus, only when the reading field is still empty — never overwriting a manually entered value. Given names are deliberately excluded: unlike family names, their readings ("nanori") are too idiosyncratic to guess reliably, so they still need to be typed in by hand. `furigana_last_name`/`furigana_first_name` are now required fields on every user creation/edit path (main form, quick-create modal, and their server-side handlers — `storeUser()`/`updateUser()`/`quickCreateUser()`, all previously unvalidated) instead of an optional field nobody filled in; `storeUser()` (the main "new user" form) also had a pre-existing bug where it silently never saved these two fields to the `users` row at all (only into the auto-generated hiring report, and only if a store was assigned) — fixed as part of this change. `last_name`/`first_name` are now required too, for the same reason (a kanji name with no split first/last name can't be searched by reading either); `quickCreateUser()`'s old rule (either a first name or a display name) is replaced by requiring both explicitly.
- Live availability check on the email and employee code fields of the user form (`/admin/users/create|edit`, and the shift-import quick-create modal, which shares the same partial): after a short pause in typing, a call to `/admin/users/check-email` or `/admin/users/check-employee-code` marks the field red with an inline message if the value is already taken by another account, instead of only finding out after submitting. Both endpoints now accept `exclude_id` so editing a user (or re-submitting your own value) doesn't flag it as taken by yourself. The quick-create modal's own bespoke code-availability logic (partly dead — it referenced DOM ids that no longer existed in the shared form partial) was replaced by this same generic mechanism, so it also gained the live email check it never had.
- Proper 403 error page: a denied permission (e.g. `PermissionMiddleware`'s "Permission requise : shifts.import") used to render through `Application::renderError()`'s bare-bones HTML fallback because no `errors/403.php` view existed, unlike 404/405/500/503. The new view follows the same layout as its siblings (error code, translated generic message, back-to-dashboard link) and shows the technical detail — which permission key was missing — in a discreet monospace line so a manager can tell the Owner exactly what to grant. Translated in fr/en/ja.
- The RBAC permission system now covers the optional bundles too — until now, their admin pages only required "manages at least one store" and their API endpoints only required a valid token. Five new permission categories in `PermissionCatalog` (`timeoff` view/create/update/approve/delete, `swaps` view/create/update/approve/delete, `timeclock` view/update/delete, `open_shifts` view/publish/approve, `feedbacks` view/update/delete), and the report-style bundles reuse existing categories (HiringReport/ResignationReport/StorePhoto → `documents.*`, SalaryReport → `payroll.*`, reactivating a resigned user → `employees.update`). `PermissionMiddleware` was added to the admin route groups of TimeOff, ShiftSwap, Timeclock, ShiftClaim, Feedback, HiringReport, ResignationReport, SalaryReport and StorePhoto with the matching `config/permissions.php` entries, and `ApiPermissionMiddleware` to the API groups of TimeOff, ShiftSwap, Timeclock, ShiftClaim and Feedback with the matching `config/api-permissions.php` rules. The API "self" rule now also reads the targeted `user_id` from the request body (POST/JSON), so an employee token can still clock **itself** in/out, list its own time-off requests or claims, and submit its own feedback without any permission — while doing any of that for someone else now requires the mapped key (previously any token could clock in/out **any** employee). A data migration (`2026_07_14_000005`) grants the new keys to every existing role holding `shifts.update` (manager-like roles), so current managers keep their access; `MANAGER_DEFAULTS` includes them for fresh installs. The manager sidebar now hides the Timeclock/Time-off/Swaps/Open-shifts/Reports/Photos links a user's roles don't grant. DailyReport keeps its own store-configurable permission system (its RBAC migration is tracked separately) and Messaging stays self-service (participant-scoped in its controllers). Docs updated (wiki API Reference & Security Overview, en/fr/ja).
- The role form (`/admin/roles`) is now bundle-aware: permission categories carried by a disabled bundle are hidden from the matrix (their routes don't exist anyway), driven by a new `PermissionCatalog::CATEGORY_BUNDLES` map. Grants already saved for a hidden category survive an edit round-trip (the controller merges them back on save) and reappear when the bundle is re-enabled.
- The RBAC permission matrix now actually gates the admin web pages, instead of any managing role granting full manager access: a new `PermissionMiddleware` (added to the `/admin` route group after `AdminMiddleware`) reads the required permission for the matched route from a new declarative `config/permissions.php` map (route name → `PermissionCatalog` key, covering the employees/stores/shifts/shift-types/payroll-stats domains) and rejects the request with a 403 when none of the user's roles grants it. When the permission is granted per-store, `managed_store_ids` is narrowed to the stores where **that specific permission** is held (not just "any permission"), so every controller's existing store filtering automatically scopes data per permission — e.g. a role with `shifts.view` on store A and `employees.view` on store B sees only store A's planning and only store B's staff. Owner (system role) bypasses all checks, routes absent from the map keep the previous coarse behavior (bundle admin pages will be mapped separately), and the default Manager role holds every mapped key so existing managers notice no change. The sidebar now hides the Staff/Stores/Planning/Reports links a user's roles don't grant (`user_can` view helper shared by the middleware), and the matched route's name is now attached to the request (`route_name` attribute) by `Application::dispatch()`.

- Salary reports can now be created per employee, not just per store: a new nullable `user_id`/`employee_name` on `salary_reports` (migration `2026_07_15_000001`) marks a report as scoped to one employee instead of the whole store. Triggered from the 💰 button on `/admin/users` (which used to link with a non-functional `employee_name` query param — now correctly passes `user_id`), it pre-fills hours/pay from that employee's own shifts only (not the store-wide totals) and shows their name throughout (form, detail page, PDF, list). The old unique constraint on `(store_id, target_month)` — one report per store per month — is now `(store_id, target_month, user_id)`, so a store-wide report and any number of per-employee reports can coexist for the same month; the "already exists" duplicate check is scoped accordingly.
- The employee management page (`/admin/users`) can now export the currently filtered list as PDF or JSON (`PdfCjkFontResolver`-backed PDF, so employee names in Japanese render correctly), covering name/employee code/email/phone/mobile/address/assigned stores/status and per-shift-type hourly rates. Respects the existing store filter and permissions (`employees.view`, same as the list itself). New `Response::jsonDownload()` for browser-downloadable JSON, alongside the existing `csv()`/`pdf()`.
- The Owner's "all stores" salary and resignation report pages (`/admin/reports/salary`, `/admin/reports/resignation`) can now export the currently filtered list as PDF or JSON, next to the existing single-report PDF button. Salary export respects the store/year/month/person filters already on the page; resignation export respects the store filter. Gated by the same permission as the list itself (`payroll.view`/`documents.view`).
- Switching the update channel to Alpha or Beta on `/admin/update` now asks for confirmation first (same pattern as the "update now" button), since those channels ship builds that are still being tested. Switching back to Release, or clicking the already-active channel's (disabled) button, doesn't prompt. Translated in fr/en/ja.
- The feedback/bug-report modal (footer button, "L'application" category for bugs) is now available on admin/owner pages too, not just employee ones, and every submission auto-attaches technical context for triage: the page it was sent from, the installed app version (`UpdateService::getCurrentVersion()`), and whether it came from a mobile or desktop browser (detected from the `User-Agent` header) — shown as a hint line under the message on `/admin/feedbacks`. Since the Owner (and any global-scope role) isn't necessarily a member of any store (`install.php` only assigns a global role, no `store_user` row), `employee_feedbacks.store_id` is now nullable (migration `2026_07_15_000004`) instead of blocking submission with a `no_store` error; a store-scoped manager still can't see or delete a storeless report, only the Owner can (`/admin/feedbacks` list and delete already scope by `managed_store_ids`). New columns `page_path`/`app_version`/`device_type` added by migration `2026_07_15_000003`.
- A "danger zone" on `/admin/backup` lets the Owner reset the application: **Reset data** wipes every operational table (shifts, timeclocks, time off, swaps, reports, feedbacks, messages, photos, notifications, activity log...) while keeping the Owner account, stores, roles and app settings — with optional checkboxes to also keep stores/shift-types-and-rates/UI-preferences, everything else is wiped by default. **Full (factory) reset** additionally wipes users/roles/settings and removes `storage/installed.lock`, sending the next request back through the web installer. Both go through a mandatory two-step flow (new `AppResetController::prepare()`/`execute()`, new `AppResetService`): a backup is always created first and its download auto-triggered on a confirmation page (new `GET /admin/backup/download`, `Response::fileStream()`) before the irreversible action can be confirmed. A plain-text `storage/logs/reset.log` entry (who/when/mode/kept categories) survives the wipe since the DB-backed audit log doesn't.
- The "New report" button on `/admin/reports/salary` and `/admin/reports/resignation` is now always visible, even before a store is picked in the filter: it opens a small "choose a store" dropdown menu (new `.store-picker` component) that links straight to that store's create form, instead of just disappearing when browsing "all stores". `/admin/reports/resignation` gained the same year/month/person-in-charge filter bar already on the salary page (filtering `resignation_date`'s year/month and `person_in_charge`, `DatabaseResignationReportRepository::findAll()` gained a `$filters` param mirroring the salary repository), and `/admin/daily-reports`'s filter bar was restyled to match both (`card--filters`/`shifts-filters__row`) instead of its previous plain `form-flex` layout — all three report list pages now look consistent. ### Fixed
- The installer no longer fails with "Database file at path [...] does not exist." when `storage/app/database.sqlite` is missing (e.g. after an incomplete or deleted previous install) — the file and its directory are now created automatically before the framework boots.
- `docs/releasing.md` (and its FR/JA translations) still pointed to `/admin/backup` for the self-update UI; fixed to `/admin/update`, matching the settings-tab split.
- **Security:** the Messaging and DailyReport bundles' `/api/v1/*` routes were registered without `ApiAuthMiddleware`, unlike every other `/api/v1/*` endpoint — they were reachable without a Bearer token even though their controllers assumed an authenticated `auth_user`. Both bundles' `routes.php` now wrap their API routes in the same protected group as the core API.
- **Critical:** shift swap requests were completely broken — creating, accepting, or refusing a swap wrote/read the columns `target_id`/`peer_accepted_at`, which don't exist in the `shift_swap_requests` table (real columns: `target_user_id`/`accepted_at`). Every attempt to create a swap threw a SQL error, and swap statistics silently under-counted the target side. Fixed in `EmployeeController`, `AdminSwapController`, the swap views, the dashboard, and `StoreStatsService`.
- `DELETE /api/v1/notifications/{id}` marked the notification as read instead of deleting it. `NotificationRepositoryInterface` gained a `delete()` method and the endpoint now actually deletes.
- `scripts/db-migrate.php --dry-run` was documented but never implemented — the script read no CLI arguments at all. It now lists pending migrations without applying them.
- `scripts/docker-setup.php` hashed the admin password with a different bcrypt cost than `install.php`/`provision.php`; aligned to cost 12.
- `.env.example` was missing several variables actually read via `env()` elsewhere (`DB_PREFIX`, `DB_CHARSET`, `DB_COLLATION`, `DB_DRIVER`, `SESSION_NAME`, `SESSION_LIFETIME`, `SESSION_SECURE`, `SESSION_HTTPONLY`, `SESSION_SAMESITE`, `APP_NAME`, `APP_VERSION`); added with their real defaults.
- **Critical:** disabling a bundle from `/admin/bundles` crashed the dashboard and sidebar with a 500 ("Route [...] not defined") for every user whose store still had the corresponding `store_features` slug checked (and unconditionally for Owner accounts, since the per-store toggle is bypassed for them). The sidebar, bottom nav, and both dashboards generated `route_url()` links to bundle-owned routes based only on the per-store toggle, never on whether the bundle itself was still enabled instance-wide. Added `FeatureManager::STORE_FEATURE_BUNDLE_MAP` (single source of truth for the store-feature-slug → bundle-slug mapping, replacing `AdminStoreController`'s private copy) plus two helpers, `bundle_enabled()`/`feat_bundle()`, now consulted everywhere a bundle-gated route is linked: the three independent `$feat()` closures (`app.php`, `dashboard/index.php`, `employee/dashboard.php`), the Owner/Manager branches of `_sidebar.php` (the Owner branch previously had no bundle check at all), `_bottomnav.php` (hrefs are now lazy closures, since the nav-item pool array previously called `route_url()` unconditionally for every item before the per-item visibility filter ran), the "feedbacks" settings tab, and the "request a swap" button on the three shift-calendar/timeline views.
