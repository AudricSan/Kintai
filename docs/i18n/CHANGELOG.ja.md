# Changelog（変更履歴）

🌐 [English](../../CHANGELOG.md) · [Français](CHANGELOG.fr.md) · **日本語**

Kintaiの主要な変更履歴をここに記録しています。

## [Unreleased]

## [0.7.6] - 2026-07-16

### 修正
- 完全（工場出荷時）リセット（`/admin/backup` の危険ゾーン）の後、Webインストーラーで再インストールすると、`roles` テーブルが永久に空のままになる不具合を修正しました。Owner/Manager/Employé を作成するseedマイグレーションは重複挿入を防ぐガードを自分自身に持っていますが、`resetFactory()` は `migrations` テーブルを除くすべてのテーブルのデータを消去するため、このマイグレーションは「すでに適用済み」としてマークされたままになり、そのガードが永久に静かにreseedをブロックしていました。マイグレーションは、`AppResetService` がマイグレーション名をハードコードする代わりに、自分自身をseedとして宣言できるようになりました（`Migration::isSeed()`）。`MigrationRunner::getSeedMigrationNames()` がそれらを公開し、`resetFactory()` は（テーブルを空にする前に、後にではなく）それらのトラッキングを解除するため、両者の間で中断が発生しても同じデータ損失は再現されず、次回のインストールで再実行されreseedされます。

## [0.7.5] - 2026-07-15

### セキュリティ
- **破壊的変更（API）**：`/api/v1/*` はRBAC認可を適用するようになりました — これまでは、認証済みトークン（一般従業員のものも含む）さえあれば、すべての店舗のすべてのリソースを読み書きできました。新しい `ApiPermissionMiddleware`（`/api/v1` グループで `ApiAuthMiddleware` の後）が、各ルートを宣言的な `config/api-permissions.php` マップ（ルート名 → `PermissionCatalog` キー、任意の「self」ルール付きで、ユーザーは自分自身のサブリソース — 自分のプロフィール、自分の設定/レート/iCalトークン — に権限なしでアクセス可能）と照合します。リクエストが特定の店舗（ルートパラメータ、クエリパラメータ、または本文フィールドの `store_id`）を対象とする場合、その権限は**その店舗向けに**付与されている必要があります（またはグローバルスコープのロールを通じて）。それ以外の場合は、どこかで保持していれば十分です。Owner はシステムロールによってすべてを通過し、トークン保有者の操作（`/auth/*`）は除外されます。管理者向けの読み取りに従業員レベルのトークンを使っていた既存の連携は、対応する権限を付与するロールを持つユーザーのトークンが必要になり、`403 {"code": "FORBIDDEN"}` を受け取るようになります。バンドルのAPIエンドポイント（休暇、シフト交換、打刻、シフト応募、メッセージ、フィードバック、日報）はまだマッピングされておらず、今のところトークンのみの認証のままです。
- **破壊的変更（API）**：`/api/v1/notifications*` は厳密に個人専用になりました：すべてのエンドポイントはトークン保有者自身の通知だけを操作します。**他のユーザー**の通知を読み取ったり、既読にしたり、一括既読にしたりできた `?user_id=` パラメータは廃止され（無視されます）、他人の通知をidで取得/削除しようとすると、漏洩・破壊する代わりに404が返るようになりました。

### 追加
- `/admin/users` の従業員検索フィールドは、入力した文字種に関わらず一致するようになり、サーバーへの往復なしで即座に絞り込みます（入力中にページの再読み込みが発生しないのは他のすべてのフィルターと異なる点です — 下記の「フィルターバーが即座に適用される」変更を参照）：漢字で名前が保存されている従業員（例：山田太郎）は、ローマ字読み（「yamada」）、ひらがな（やまだ）、カタカナ（ヤマダ）を入力しても、漢字そのものでなくても見つかるようになりました。各行は検索用テキストとふりがなの読みをデータ属性として保持し（`data-search-text`/`data-search-reading`、`furigana_last_name`/`furigana_first_name` から設定 — ユーザーフォームで既に収集されていたが、これまでPDF/レポート表示にしか使われていなかった）、新しい `kana-search.js` モジュール（マッチングアルゴリズムのJS移植版で、他の場所で使われ `KanaSearchTest` でテストされているPHPの `KanaSearch` サービスと同期）が、ローマ字クエリをカタカナに変換し（ヘボン式テーブル、促音/拗音/モーラ音のんを処理）、ひらがな/カタカナの入力を正規化します — すべてクライアント側で処理されます。読みが利用できない場合は、名前/従業員コード/メールアドレスに対する単純な部分文字列一致にフォールバックします — ふりがなは任意項目で誰も入力してこなかったため、現状ではほとんどの従業員がこれに該当します。読みベースの一致は、この項目が入力されて初めて役立ちます。この障壁を下げるため、ユーザー作成/編集フォーム（およびシフトインポートのクイック作成モーダル、同じ共有パーシャルを使用）は、`last_name` がフォーカスを失うと、約160件の日本人の一般的な姓の辞書（新しい `furigana-suggest.js`）から `furigana_last_name` を自動提案するようになりました。ただし読みフィールドがまだ空の場合のみで、手動で入力された値を上書きすることはありません。名（下の名前）は意図的に除外されています：姓とは異なり、その読み（「名乗り」）は推測するには特異すぎるため、引き続き手入力が必要です。`furigana_last_name`/`furigana_first_name` は、すべてのユーザー作成/編集の経路（メインフォーム、クイック作成モーダル、およびそのサーバー側ハンドラ — `storeUser()`/`updateUser()`/`quickCreateUser()`、これまで検証されていなかった）で必須項目になりました。誰も入力してこなかった任意項目から変わりました。`storeUser()`（メインの「新規ユーザー」フォーム）には、この2つのフィールドが `users` 行に一切保存されない（雇用レポートに自動生成される場合のみ、しかも店舗が割り当てられている場合のみ）という既存のバグもあり、この変更の一環として修正されました。同じ理由（分離された姓名のない漢字名は読みでも検索できない）で `last_name`/`first_name` も必須になりました。`quickCreateUser()` の旧ルール（名または表示名のいずれか）は、両方を明示的に必須とするルールに置き換えられました。
- ユーザーフォーム（`/admin/users/create|edit`、および同じパーシャルを共有するシフトインポートのクイック作成モーダル）のメールアドレスと従業員コードのフィールドにリアルタイム空き確認を追加：入力の一時停止後、`/admin/users/check-email` または `/admin/users/check-employee-code` への呼び出しが、値が既に別のアカウントで使われている場合にフィールドを赤くしてインラインメッセージを表示します。送信後に初めて分かるのではなく。両エンドポイントとも `exclude_id` を受け付けるようになり、ユーザーの編集（または自分自身の値の再送信）が自分自身に取られていると誤検知されなくなりました。クイック作成モーダル独自のコード空き確認ロジック（一部はデッドコードで、共有フォームパーシャルにもう存在しないDOM idを参照していました）は、この同じ汎用メカニズムに置き換えられ、これまで持っていなかったリアルタイムのメール確認も獲得しました。
- 正しい403エラーページ：権限拒否（例：`PermissionMiddleware` の「Permission requise : shifts.import」）は、`errors/403.php` ビューが存在しなかったため、404/405/500/503とは異なり `Application::renderError()` の簡素なHTMLフォールバックを経由していました。新しいビューは兄弟ページと同じレイアウトに従い（エラーコード、翻訳された一般メッセージ、ダッシュボードへ戻るリンク）、どの権限キーが不足していたかという技術的な詳細を、マネージャーがOwnerに何を付与すべきか正確に伝えられるよう、控えめな等幅フォントの行で表示します。fr/en/jaに翻訳済みです。
- RBAC権限システムがオプションのバンドルもカバーするようになりました — これまでは、それらの管理ページは「少なくとも1つの店舗を管理している」ことのみを要求し、APIエンドポイントは有効なトークンのみを要求していました。`PermissionCatalog` に5つの新しい権限カテゴリ（`timeoff` の view/create/update/approve/delete、`swaps` の view/create/update/approve/delete、`timeclock` の view/update/delete、`open_shifts` の view/publish/approve、`feedbacks` の view/update/delete）が追加され、レポート系バンドルは既存のカテゴリを再利用します（HiringReport/ResignationReport/StorePhoto → `documents.*`、SalaryReport → `payroll.*`、退職した従業員の再有効化 → `employees.update`）。`PermissionMiddleware` が TimeOff、ShiftSwap、Timeclock、ShiftClaim、Feedback、HiringReport、ResignationReport、SalaryReport、StorePhoto の管理ルートグループに、対応する `config/permissions.php` エントリと共に追加され、`ApiPermissionMiddleware` が TimeOff、ShiftSwap、Timeclock、ShiftClaim、Feedback のAPIグループに、対応する `config/api-permissions.php` ルールと共に追加されました。APIの「self」ルールは、リクエスト本文（POST/JSON）から対象の `user_id` も読み取るようになったため、従業員トークンは権限なしで**自分自身**を打刻したり、自分自身の休暇申請やシフト応募を一覧表示したり、自分自身のフィードバックを送信したりできます — 他の誰かに対して同じことをするにはマッピングされたキーが必要になりました（これまではどのトークンでも**任意の**従業員を打刻できました）。データマイグレーション（`2026_07_14_000005`）が、`shifts.update` を持つ既存のすべてのロール（マネージャー相当のロール）に新しいキーを付与するため、現在のマネージャーはアクセス権を維持します。`MANAGER_DEFAULTS` には新規インストール向けにこれらが含まれます。マネージャーのサイドバーは、ユーザーのロールが許可しない打刻/休暇/シフト交換/オープンシフト/レポート/写真のリンクを非表示にするようになりました。DailyReportは独自の店舗別設定可能な権限システムを維持し（そのRBACマイグレーションは別途管理されています）、Messagingはセルフサービスのままです（コントローラー内で参加者に限定）。ドキュメントを更新しました（wikiのAPIリファレンスとセキュリティ概要、en/fr/ja）。
- ロールフォーム（`/admin/roles`）はバンドルを認識するようになりました：無効化されたバンドルが持つ権限カテゴリはマトリクスから非表示になります（そのルートはそもそも存在しないため）。新しい `PermissionCatalog::CATEGORY_BUNDLES` マップによって制御されます。非表示のカテゴリに既に保存された権限は編集の往復を経ても保持され（コントローラーが保存時に再統合します）、バンドルが再有効化されると再表示されます。
- RBAC権限マトリクスが、管理系ロールなら何でもフルのマネージャーアクセスを与えるのではなく、実際に管理Webページを制御するようになりました：新しい `PermissionMiddleware`（`/admin` ルートグループに `AdminMiddleware` の後に追加）が、一致したルートに必要な権限を新しい宣言的な `config/permissions.php` マップ（ルート名 → `PermissionCatalog` キー、従業員/店舗/シフト/シフト種別/給与統計のドメインをカバー）から読み取り、ユーザーのどのロールもそれを許可しない場合は403でリクエストを拒否します。権限が店舗ごとに付与されている場合、`managed_store_ids` は「何らかの権限」ではなく**その特定の権限**を保持している店舗に絞り込まれるため、各コントローラーの既存の店舗フィルタリングが権限ごとに自動的にスコープされます — 例えば、店舗Aで `shifts.view`、店舗Bで `employees.view` を持つロールは、店舗Aのプランニングと店舗Bのスタッフしか見えません。Owner（システムロール）はすべてのチェックをバイパスし、マップにないルートは以前の粗い挙動を維持し（バンドルの管理ページは別途マッピングされます）、デフォルトのManagerロールはマップされたすべてのキーを持つため既存のマネージャーは変化に気づきません。サイドバーは、ユーザーのロールが許可しないスタッフ/店舗/プランニング/レポートのリンクを非表示にするようになり（ミドルウェアと共有される `user_can` ビューヘルパー）、一致したルート名が `Application::dispatch()` によってリクエストに付加されるようになりました（`route_name` 属性）。

- 給与レポートは店舗ごとだけでなく、従業員ごとにも作成できるようになりました：`salary_reports` に新しいnullableな `user_id`/`employee_name`（マイグレーション `2026_07_15_000001`）が追加され、レポートを店舗全体ではなく1人の従業員に紐づくものとしてマークします。`/admin/users` の💰ボタン（以前は機能しない `employee_name` クエリパラメータでリンクしていましたが、現在は正しく `user_id` を渡します）から起動し、その従業員自身のシフトのみ（店舗全体の合計ではなく）から時間/給与を事前入力し、フォーム、詳細ページ、PDF、一覧全体にその名前を表示します。`(store_id, target_month)`（店舗と月ごとに1レポート）の旧ユニーク制約は `(store_id, target_month, user_id)` になったため、店舗全体のレポートと任意の数の従業員別レポートが同じ月に共存できます。「既に存在します」の重複チェックもそれに応じて絞り込まれます。
- 従業員管理ページ（`/admin/users`）は、現在フィルターされている一覧をPDFまたはJSONとしてエクスポートできるようになりました（日本語の従業員名が正しくレンダリングされるよう `PdfCjkFontResolver` を使用したPDF）。名前/従業員コード/メール/電話/携帯/住所/割り当てられた店舗/ステータス、シフト種別ごとの時給をカバーします。既存の店舗フィルターと権限（一覧自体と同じ `employees.view`）を尊重します。ブラウザでダウンロード可能なJSON用の新しい `Response::jsonDownload()` が、既存の `csv()`/`pdf()` に加わりました。
- Ownerの「全店舗」給与・退職レポートページ（`/admin/reports/salary`、`/admin/reports/resignation`）は、既存の単一レポートPDFボタンに加えて、現在フィルターされている一覧をPDFまたはJSONとしてエクスポートできるようになりました。給与エクスポートはページ上の既存の店舗/年/月/担当者フィルターを尊重し、退職エクスポートは店舗フィルターを尊重します。一覧自体と同じ権限（`payroll.view`/`documents.view`）で制御されます。
- `/admin/update` で更新チャンネルをAlphaまたはBetaに切り替える際、事前に確認を求めるようになりました（「今すぐ更新」ボタンと同じパターン）。これらのチャンネルはまだテスト中のビルドを配信するためです。Releaseに戻す、または既にアクティブなチャンネルの（無効化された）ボタンをクリックする場合は確認を求めません。fr/en/jaに翻訳済みです。
- フィードバック/バグ報告モーダル（フッターボタン、バグ用の「アプリケーション」カテゴリ）は、従業員ページだけでなく管理者/オーナーページでも利用できるようになり、すべての送信にトリアージ用の技術的コンテキストが自動的に添付されます：送信元のページ、インストール済みのアプリバージョン（`UpdateService::getCurrentVersion()`）、モバイルまたはデスクトップブラウザのどちらから来たか（`User-Agent` ヘッダーから検出）— `/admin/feedbacks` のメッセージの下にヒント行として表示されます。Owner（および他のグローバルスコープのロール）は必ずしもどこかの店舗のメンバーであるとは限らないため（`install.php` はグローバルロールのみを割り当て、`store_user` 行は作成しません）、`employee_feedbacks.store_id` は `no_store` エラーで送信をブロックする代わりに、nullable（マイグレーション `2026_07_15_000004`）になりました。店舗限定のマネージャーは、店舗のない報告を見たり削除したりすることは依然としてできず、Ownerのみが可能です（`/admin/feedbacks` の一覧と削除は既に `managed_store_ids` でスコープされています）。マイグレーション `2026_07_15_000003` により新しい列 `page_path`/`app_version`/`device_type` が追加されました。
- `/admin/backup` の「危険ゾーン」で、Ownerがアプリケーションをリセットできるようになりました：**データのリセット**は、Ownerアカウント、店舗、ロール、アプリ設定を保持しつつ、すべての運用テーブル（シフト、打刻、休暇、シフト交換、レポート、フィードバック、メッセージ、写真、通知、活動ログ...）を消去します — 店舗/シフト種別と時給/UI設定も保持するオプションのチェックボックス付きで、それ以外はデフォルトで消去されます。**完全（工場出荷時）リセット**は、さらにユーザー/ロール/設定も消去し、`storage/installed.lock` を削除して、次のリクエストをWebインストーラーに送り返します。どちらも必須の2段階フロー（新しい `AppResetController::prepare()`/`execute()`、新しい `AppResetService`）を経ます：不可逆的な操作が確認される前に、まずバックアップが常に作成され、確認ページ（新しい `GET /admin/backup/download`、`Response::fileStream()`）でそのダウンロードが自動的にトリガーされます。データベース上の監査ログは消去を生き延びないため、プレーンテキストの `storage/logs/reset.log` エントリ（誰が/いつ/どのモード/保持したカテゴリ）が消去を生き延びます。
- `/admin/reports/salary` と `/admin/reports/resignation` の「新規レポート」ボタンは、フィルターで店舗が選択される前でも常に表示されるようになりました：小さな「店舗を選択」ドロップダウンメニュー（新しい `.store-picker` コンポーネント）を開き、その店舗の作成フォームに直接リンクします。「全店舗」を閲覧しているときに単に消えるのではなく。`/admin/reports/resignation` は給与ページに既にあるのと同じ年/月/担当者フィルターバーを獲得し（`resignation_date` の年/月と `person_in_charge` をフィルター、`DatabaseResignationReportRepository::findAll()` が給与リポジトリを反映する `$filters` パラメータを獲得）、`/admin/daily-reports` のフィルターバーは、以前の単純な `form-flex` レイアウトの代わりに両方に合わせて（`card--filters`/`shifts-filters__row`）再スタイルされました — 3つのレポート一覧ページすべてが一貫した見た目になりました。退職レポートの作成/編集フォームでは、「Utilisateur」ドロップダウンが、アプリ内のすべてのユーザーではなく対象店舗のメンバーに絞られるようになりました（レポートに既にリンクされている従業員がメンバーでなくなっていても引き続き含まれるため、古いレポートを編集しても選択が黙って失われることはありません）。リストから誰かを選択すると、従業員番号/名前フィールドがクライアント側で自動入力されるようになりました。共有の「Responsable」ピッカー（`HasStaffReportCrud::getManagersForReportForm()`、給与と退職の両フォームで使用）には、他のグローバルスコープのロールと同様、特定の店舗の `store_user` メンバーとは限らないOwnerが常に含まれるようになりました。
- 単一店舗の給与レポートページ（`/admin/stores/{id}/reports/salary`）は、`/admin/users` の💰ボタンからだけでなく、直接従業員別レポートを作成できるようになりました：その「新規レポート」ボタンは、同じ `.store-picker` ドロップダウンパターンを開き、「店舗全体のレポート」エントリの後に店舗の従業員が続き、それぞれがその従業員をプリセットした状態で作成フォームに直接リンクします。`HasStaffReportCrud` は（既存の `reportEditExtras()` を反映した）`reportListExtras()` フックを獲得し、`AdminSalaryReportController` は `ResignationReportController`（デフォルトは空）に影響を与えることなく、店舗のメンバーを一覧ビューに渡せるようになりました。

- RBACの切り替え：`AuthService::isAdmin()`/`managedStoreIds()`/`isManager()` は、`users.is_admin`/`store_user.role` の代わりに `role_assignments` から計算されるようになりました — この変更は `AuthService::user()` に隔離されており、返されるユーザー配列に有効な `is_admin` 値を重ね合わせるため、`$request->getAttribute('auth_user')['is_admin']` を読み取る既存のすべてのコントローラー/ビュー（`BackupController`、`BundleSettingsController`、`OwnerSettingsController`、`LanguageController`、`AdminController`、`EmployeeController`、`DailyReportPermissionService` などのOwner専用ゲート）は変更なしで動作し続けます。新しいマイグレーション（`2026_07_14_000004_backfill_role_assignments`）が、デプロイ/自己アップデートのたびに `scripts/migrate-roles.php` と同じ逆補填を自動的に実行するため、既存のインスタンスが `AuthService` が空の `role_assignments` テーブルを読み取る状態に陥ることはありません。新しい `RoleAssignmentSyncService` は、今後も `role_assignments` を同期し続けます：ユーザーのOwnerフラグの作成/編集（`AdminUserController::storeUser()`/`updateUser()`/`quickCreateUser()`）と店舗メンバーシップの追加/変更/削除（`AdminStoreController::addMember()`/`updateMemberRole()`/`removeMember()`）は、レガシーカラムだけでなく、対応するロール割り当ても書き込むようになりました。インストーラー（`public/install.php`）も同じ理由で、作成するアカウントにOwnerロールを割り当てます。`DailyReportPermissionService` とAPIは変更を必要としませんでした — 前者は `store_user.role`（変更なし）とブリッジされた `is_admin` のみを直接読み取り、後者は依然として認可レイヤーを持っていません（別途管理）。

- オーナーは、サーバー上で手動で `git clone` する代わりに、`/docs` から直接ローカルwiki（`.wiki/`）をクローンまたは更新できるようになりました：新しい `WikiSyncService` が、wikiの `_Sidebar.md` に列挙されている全ページ（3言語分）を `raw.githubusercontent.com/wiki/{repo}/...` から単純なHTTPS経由で取得します — `git` バイナリや `exec()` は不要で、`GithubUpdateService` の自己アップデート機構と同じ、共有ホスティングに適した方式です。冪等な `sync()` を1回呼び出すだけで両方のケースに対応します：初回実行時（ローカルに何もない状態）はすべてをクローンし、以降の実行では実際に内容が変わったページのみを再書き込みし、変更のないページはスキップし、翻訳が存在しない場合（HTTP 404）はエラーではなく正常なケースとして扱います。`POST /docs/sync`（`DocsController::sync()`、オーナー限定、`BackupController`／`LanguageController` と同じ `requireOwner()` パターンに準拠）として公開され、`/docs` にはオーナー向けに「wikiをクローン」／「wikiを更新」ボタンが表示され、追加／更新／変更なしの件数が報告されます。`WikiSyncService` のコンストラクタはnullableな `\Closure`（テスト専用のフェッチャー差し替え）を受け取るため、コンテナのリフレクションによる自動解決だけではインスタンス化できず、`AppServiceProvider` に明示的なシングルトンバインディングが必要でした — `GithubUpdateService` が既に同様のバインディングを必要としていたのと同じ理由です。
