# Architecture : Kintai

🌐 [English](../architecture.md) · **Français** · [日本語](architecture.ja.md)

## 🏗 Conception générale
Kintai suit une architecture MVC (Model-View-Controller) modulaire, conçue pour une portabilité et un isolement extrêmes.

### 1. Le modèle « single-tenant orchestré »
Kintai n'est pas un SaaS à infrastructure partagée.
- **Plan de données :** chaque propriétaire (tenant) dispose d'une instance dédiée de l'application et d'une base de données dédiée.
- **Plan de contrôle :** une couche d'orchestration centrale (Kintai SaaS) gère le cycle de vie de ces instances (provisioning, mises à jour, sauvegardes).

### 2. Composants principaux
- **Application cœur :** framework PHP 8.3 sur mesure suivant les principes PSR-12 et SOLID.
- **Router :** router regex sur mesure gérant les routes Web, API et Cron.
- **Container :** conteneur d'injection de dépendances (DI) léger pour la gestion des services.
- **Middleware :** un pipeline pour les préoccupations transverses (Auth, i18n, Sécurité).

## 📊 Couche de données (Eloquent ORM)
Kintai utilise **Eloquent en mode standalone** (`illuminate/database`) comme unique ORM.
- Les **repositories** encapsulent les modèles Eloquent pour préserver le découplage du domaine ; les contrôleurs n'utilisent jamais les modèles directement.
- **Drivers :** SQLite (par défaut) et MySQL.
- **Migrations :** basées sur PHP, unifiées (`database/migrations/php/`) — plus de fichiers SQL bruts.
- L'ancien `PersistenceDriverInterface` et JsonDB ont été supprimés.

## 🧩 Bundles modulaires
Les fonctionnalités au-delà du cœur toujours actif sont livrées sous forme de bundle, soit encore dans le monorepo (`src/Bundles/*/`), soit distribuées indépendamment (voir "Bundles distribués" ci-dessous) — le Core se limite désormais à Shift, User et Store, plus l'infrastructure transversale (auth, i18n, notifications, réglages, cron, ...). Congés, Échanges de shifts, Pointage et Rapports journaliers sont des exceptions partielles : `TimeoffRequestRepositoryInterface`, `ShiftSwapRequestRepositoryInterface`, `TimeclockRepositoryInterface` et `DailyReportRepositoryInterface` restent tous des services Core (plusieurs composants Core — stats magasin, service de planification, contrôleur admin des shifts, export iCal, `HomeController`, tableau de bord employé, `DailyReportNavMiddleware`, le cron d'auto-validation — lisent ces données pour des calculs qui doivent continuer de fonctionner quoi qu'il arrive), donc désactiver ou désinstaller l'un de ces quatre bundles retire son UI de gestion mais pas les données sous-jacentes ni ces calculs Core. Rapports journaliers va plus loin que les trois autres : ses services permission/PDF/mail/auto-validation (`DailyReportPermissionService`/`PdfService`/`MailService`/`AutoValidateService`) sont eux aussi liés côté Core (`AppServiceProvider`), pas seulement son repository — découvert à la dure en extrayant ce bundle du monorepo, ce qui a cassé toute page authentifiée (`DailyReportNavMiddleware` est un middleware global, pas filtré par le bundle du tout). Le toggle par store `timeclock` déjà existant se filtre aussi sur le bundle via `AdminStoreController::FEATURE_BUNDLE_MAP`, comme `messages`/`daily_reports`/`photos`. Bourse aux shifts est différent : aucun composant Core ne lit directement ses données, donc `ShiftClaimRepositoryInterface` a été déplacé dans le bundle lui-même plutôt que de rester un service Core — le désactiver retire entièrement la fonctionnalité, données comprises. Son extraction a aussi nécessité de scinder les six méthodes open-shifts/publish/claim hors d'`AdminShiftController` (Core) et d'`EmployeeController` (Core), qui mélangeaient auparavant la logique de bourse aux shifts avec les contrôleurs de planification toujours actifs. Embauche, démission et salaire partageaient auparavant un seul `AdminReportController` avec un dispatch interne `repo(string $type)` ; ce contrôleur a désormais entièrement disparu, remplacé par trois contrôleurs de bundle (`AdminResignationReportController`, `AdminSalaryReportController`, `AdminHiringReportController`) partageant la logique CRUD/PDF via un trait réutilisable `HasStaffReportCrud`. La méthode `calculateSalaryPreset()` de salaire lit `DailyReportRepositoryInterface` (liée côté Core, voir ci-dessus) pour pré-remplir le chiffre d'affaires du mois. Contrairement à démission/salaire, `HiringReportRepositoryInterface` reste un service Core plutôt que de rejoindre son bundle : `AdminUserController` le lit/écrit directement pour générer automatiquement un rapport d'embauche à chaque création d'employé (formulaire standard et import Excel rapide), un mécanisme du cœur de la gestion des utilisateurs qui doit continuer de fonctionner même si le bundle hiring-report est désactivé — le désactiver ne retire que l'UI de consultation/édition/PDF, pas cette génération automatique ni les données. Feedback est une extraction complète (comme Store Photos) : aucun autre composant Core ne lit les données de feedback, donc `FeedbackRepositoryInterface` est enregistré par le bundle lui-même. Une subtilité : la modale de soumission de feedback est incluse directement par le layout partagé `app.php` sur chaque page employé (pas via les vues propres du bundle), donc `AuthMiddleware` partage un indicateur `feedback_enabled` que le layout vérifie avant de l'inclure — sinon la modale continuerait de s'afficher, et son POST renverrait une 404, une fois le bundle indisponible.

Chaque garde-fou de bundle côté vue (`bundle_enabled()`/`feat_bundle()` dans `src/Core/helpers.php`, utilisés dans toute la nav/sidebar/topbar/bottomnav, pas seulement la modale feedback) lit `BundleManager::isActive()` — les bundles réellement enregistrés après le boot — jamais `FeatureManager::isEnabled()` seul, qui ne reflète que le réglage stocké par instance. Les deux peuvent diverger quand un bundle est activé dans les réglages existants mais n'est plus présent sur le disque : exactement ce qui se produit au moment où un bundle est extrait du monorepo (Feedback, puis Rapports journaliers) alors que `app_settings.enabled_bundles` d'une instance le liste encore — chaque partial de nav qui construisait inconditionnellement une `route_url()` vers les pages de ce bundle a cassé la production dès que `bundle_enabled()` "fail-open" sur le réglage périmé. `AuthMiddleware`/`bundle_enabled()` sont tous deux passés par là ; toute future extraction de bundle hérite du correctif gratuitement.
- **Découverte :** `BundleDiscoveryService` fusionne deux sources au démarrage — le scan legacy du monorepo (`src/Bundles/*/`, toute classe `{Nom}\{Nom}Bundle` étendant `Bundle`, même convention PSR-4 que toujours) et les bundles installés dynamiquement (`storage/bundles/{slug}/{version}/`, résolus depuis leur propre `bundle.json`, voir "Bundles distribués" ci-dessous). Rien n'est codé en dur dans un registre pour l'une ou l'autre source ; un slug détecté par les deux (ce qui ne devrait normalement jamais arriver) est résolu en faveur du legacy, avec un avertissement journalisé.
- **Contrat stable :** `kintai\Core\BundleContract\Bundle` est la classe de base gelée, versionnée indépendamment, qu'un auteur de bundle doit étendre — un changement cassant à cet endroit est un événement documenté et annoncé au CHANGELOG, contrairement au reste de `src/Core/`, qui peut évoluer entre deux versions mineures sans préavis. `kintai\Core\Bundle` (l'ancien emplacement) était un alias de compatibilité déprécié ; il a été supprimé en prévision de la V1.0 maintenant que tous les bundles du monorepo ont migré vers `kintai\Core\BundleContract\Bundle` directement — un bundle tiers étendant encore l'ancien alias doit être mis à jour.
- **Bundles distribués :** au-delà du modèle monorepo ci-dessus, un bundle peut désormais vivre dans son propre dépôt Git, versionné indépendamment, et être installé depuis `/admin/bundles/market` sans jamais toucher au code de Kintai — sur le même principe que les dépôts d'add-ons Home Assistant. Un Owner ajoute un ou plusieurs **registries** (`/admin/bundles/registries` — une URL vers un listing statique `registry.json`, récupéré en simple HTTP par `BundleRegistryClient`, jamais cloné ; le registry officiel est ajouté par défaut et ne peut pas être supprimé), puis installe/met à jour un bundle listé via `BundleInstallerService`, qui télécharge le zipball d'une release GitHub taguée (`HttpFetcher`, même repli curl → wrapper de flux PHP que `GithubUpdateService` — jamais `git clone`/`pull`, PHP sur un hébergement mutualisé ne pouvant pas garantir l'accès à `git`), vérifie son `bundle.json` (slug correspondant, compatibilité de version Core, classe d'entrée effectivement présente) avant d'écrire quoi que ce soit, puis l'active dans `storage/bundles/{slug}/{version}/` — hors de `src/Bundles/`, donc jamais dans ce dépôt Git. Un mode dry-run exécute toutes les vérifications sans rien installer. Les bundles quittent `src/Bundles/` un par un de cette façon, chacun vers son propre dépôt (`kintai-bundle-{slug}`) distribué via le registry officiel — savoir si un bundle donné a déjà migré se résume à vérifier s'il a encore un dossier sous `src/Bundles/`. Voir `docs/creating-a-bundle.md` (source en anglais, traduit en français) pour le guide complet, destiné à quiconque — en interne ou tiers — écrit un bundle de cette façon.
- **Feature flags :** le chargement effectif d'un bundle découvert est décidé par `FeatureManager`, alimenté par `LicenseServiceProvider` — historiquement une question de déploiement (quels bundles existent sur cette instance), désormais aussi l'endroit où le quota freemium de bundles est appliqué (voir « Licences & Freemium » ci-dessous). Les Owners activent/désactivent chaque bundle au niveau de l'instance depuis `/admin/bundles` (stocké dans `app_settings.enabled_bundles`), avec repli sur `enabled_features` de `config/license.php` si rien n'est configuré. Au sein d'un bundle activé, chaque store peut ensuite l'activer ou non pour lui-même via ses propres réglages (fiche magasin).
- **Officiel ou tiers :** `config/official-bundles.php` liste les slugs des bundles réellement développés et maintenus par le projet Kintai. C'est la seule source de vérité pour cette distinction — un bundle ne peut pas s'auto-déclarer officiel. `/admin/bundles` signale comme tiers tout bundle détecté mais absent de cette liste, avec un avertissement indiquant qu'il n'est pas maintenu par le projet principal.
- **Système de hooks :** le Core fournit des points d'extension permettant aux bundles d'injecter des éléments UI, des routes API et de la logique.

## 💳 Licences & Freemium
L'auto-hébergement reste gratuit et open source pour un usage personnel ou de petite structure ; le modèle freemium est appliqué localement, sans aucun appel réseau pour l'offre gratuite. `PlanLimitService` (`src/Core/Services/`) est la source de vérité unique des limites du plan courant — pour l'instant, un plan gratuit codé en dur dans cette classe : 1 magasin actif, 15 employés actifs, 4 bundles actifs simultanément (au choix de l'Owner, modifiable à tout moment depuis `/admin/bundles` — en désactiver un libère une place pour un autre). `StoreService::createStore()` et les points d'entrée de création d'employé (`AdminUserController::storeUser()`/`quickCreateUser()`, `Api\V1\UserController::store()`) appellent `PlanLimitService::assertCanCreate*()`, qui lève une `PlanLimitExceededException` (HTTP 403, rendue comme n'importe quelle autre `HttpException`) ; `BundleSettingsController::save()` vérifie plutôt directement `PlanLimitService::maxActiveBundles()` par rapport au nombre envoyé. `Api\V1\StoreController::store()` délègue à `StoreService::createStore()` (au lieu d'appeler directement le repository, comme avant) précisément pour que ce contrôle — ainsi que la validation existante de `StoreValidator` — couvre aussi l'API, et pas seulement l'interface d'administration web ; il n'existe pas encore de `UserService` équivalent, donc la vérification côté employés est dupliquée à chacun de ses trois points d'entrée au lieu d'être centralisée.

Une licence payante lève les limites du plan gratuit ci-dessus, mais pas nécessairement jusqu'à « illimité » — chaque licence porte ses propres limites numériques (`max_stores`/`max_employees`/`max_bundles`, une map JSON libre dont les clés sont définies selon les besoins du produit, puisque d'autres produits Freemium bâtis sur le même License Manager ont des dimensions entièrement différentes), définies à partir d'un palier nommé (Starter/Pro/Business, défini par l'admin pour chaque produit, simple commodité à la création — modifier un palier par la suite ne touche jamais les licences déjà émises à partir de lui) ou saisies ponctuellement pour une licence sur mesure. `PlanLimitService::maxStores()`/`maxEmployees()`/`maxActiveBundles()` les lisent depuis `LicenseClientService::entitlements()` lorsque `isPaidPlanActive()` vaut `true` ; une clé absente de la map (ou explicitement `null`) signifie illimité pour cette dimension précisément, et une licence payante sans droits encore vérifiables (voir plus bas) est par défaut illimitée sur toutes les dimensions — le comportement d'avant les paliers, pour qu'une instance déjà payante ne soit jamais bridée en attendant sa prochaine synchronisation.

La gestion des licences est elle-même un projet séparé (« License Manager », même architecture que Kintai : front controller, Eloquent, migrations PHP), réutilisé par tous les produits Freemium, pas seulement Kintai — son API générique (`POST /activate`, `/validate`, `/deactivate`, produit identifié par `api_key`, instance par `license_key` + `instance_id`) renvoie à la fois des champs simples (`valid`/`status`/`type`/`expires_at`/…, pratiques pour les logs et le tableau de bord du License Manager) et un `license_token` signé : `base64url(payload).base64url(signature)`, Ed25519 (extension `openssl` de PHP, `algo=0` — pas l'extension `sodium`, indisponible sur certaines installations XAMPP), le payload contenant type/palier/limites/expiration/sièges de la licence. C'est délibéré, pas accessoire : l'Owner d'une instance auto-hébergée contrôle entièrement sa base de données, si bien qu'un simple indicateur « est-ce payant » ou de simples chiffres de limites mis en cache dans `app_settings` pourraient être modifiés à la main pour débloquer le plan payant. La signature comble cette faille — `LicenseTokenVerifier` (`src/Core/Services/`) vérifie la signature avec une clé publique configurée localement (`LICENSE_SERVER_PUBLIC_KEY_B64`, sans risque à distribuer puisqu'elle ne peut que vérifier, jamais forger — la clé privée correspondante ne quitte jamais le serveur du License Manager, générée via son `scripts/generate-signing-key.php`), et `PlanLimitService` ne fait confiance qu'aux limites issues d'un token vérifié. Un token prouve l'*authenticité* de ce qui a été émis, pas sa validité *actuelle* — une licence peut toujours être révoquée côté serveur après coup — la revalidation périodique existante (voir plus bas) reste donc nécessaire pour le détecter ; le token ne s'y substitue pas, les deux se combinent (vérification locale à chaque lecture des limites, réconciliation périodique avec le serveur).

`LicenseClientService` (`src/Core/Services/`) porte tout cela : il n'émet aucune requête réseau tant qu'un Owner n'a pas saisi de `license_key` sur `/admin/license`, en utilisant `HttpFetcher::post()` (même primitive curl/repli sur les streams que `BundleInstallerService`/`GithubUpdateService`, configurée via `config/license_server.php` / `LICENSE_SERVER_URL`+`LICENSE_SERVER_API_KEY`+`LICENSE_SERVER_PUBLIC_KEY_B64`). Le résultat de chaque contact avec le serveur est mis en cache dans `app_settings` (`license_key`, `license_state` — statut/type/expiration/dernière validité/dernière vérification/`license_token`) de sorte que `isPaidPlanActive()` et `entitlements()` n'aient jamais besoin d'atteindre le réseau ; un statut `degraded` (serveur injoignable lors de la dernière tentative) maintient le plan payant pendant `grace_period_days` (14 par défaut) depuis la dernière vérification confirmée valide, puis retombe en gratuit — un `valid:false` explicite du serveur (révoquée/expirée/introuvable) repasse en gratuit immédiatement, sans délai de grâce. La revalidation a lieu de manière opportuniste quand l'Owner visite `/admin/license`, et sans surveillance via le job cron `license-check` (`LicenseCheckJob`, enregistré dans `CronRunner` comme `auto-validate`/`backup`/`log-purge` — token via `scripts/create-cron-token.php --job=license-check`).

Un même achat peut aussi couvrir plusieurs produits à la fois (les « license bundles » du License Manager : un client + type/expiration partagés, une licence générée par produit sélectionné, chacune avec sa propre clé/palier/limites, regroupées uniquement pour le suivi et les actions en masse de l'admin du License Manager — le client de Kintai ne connaît pas la notion de bundle, il active simplement sa propre clé comme n'importe quelle autre).

## 🌐 Multi-tenancy
Le multi-tenancy est réalisé au **niveau du déploiement**, pas au niveau du code.
- **Isolation :** isolation physique par propriétaire.
- **Reporting inter-magasins :** géré nativement puisque tous les magasins d'un même propriétaire partagent la même instance de base de données.

## 🖥 Stratégie frontend
- **Rendu côté serveur (SSR) :** vues PHP natives pour la rapidité, la simplicité et la facilité de déploiement.
- **JS & CSS vanilla :** aucune étape de build lourde ni framework frontend, pour que l'application reste légère et facile à personnaliser.
- **Mobile first :** design responsive pensé pour les employés consultant leur planning en déplacement.

## 📡 API & Intégrations
- **API V1 :** une API RESTful permettant l'intégration avec des outils tiers.
- **iCal :** calendriers personnels pour les employés, sécurisés par token.

## ⏱ Scripts d'exploitation & CLI
Au-delà de `scripts/db-migrate.php` (voir [Stratégie de base de données](database.fr.md)) et `scripts/check-translations.php` (voir [Contribuer](CONTRIBUTING.fr.md)), quelques scripts CLI autonomes portent des tâches de maintenance récurrentes — chacun démarre l'`Application` complète et est prévu pour tourner sans interaction (cron, tâche planifiée, ou lancement manuel) :
- **`photo-retention.php`** — purge les photos de magasin uploadées au-delà de la fenêtre de rétention configurable (réglages `photo_retention_days`/`photo_cleanup_delay`).
- **`consolidate-daily-photo-reports.php`** — fusionne rétroactivement les envois de photos du même jour/magasin en un seul rapport (`--dry-run` disponible) ; voir `StorePhotoConsolidationService`.
- **`auto-validate-reports.php`** — valide automatiquement les rapports journaliers restés non validés après l'heure limite du magasin ; aussi exposé comme endpoint HTTP protégé par token (`/cron/auto-validate`) pour les planificateurs externes.
- **`create-cron-token.php`** — émet un token pour le lanceur cron générique (`/cron/run/{job}`).
- **`seed-demo-data.php`** — génère des données d'exemple réalistes sur l'ensemble des bundles pour les tests locaux (`--force` pour reseeder).
