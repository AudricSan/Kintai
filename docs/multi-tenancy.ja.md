# マルチテナンシー戦略：Kintai

🌐 [English](multi-tenancy.md) · [Français](multi-tenancy.fr.md) · **日本語**

## 🛡 基本原則
Kintaiのマルチテナンシーは**物理的分離**の原則に基づいています。共有インフラの密度よりも、セキュリティとデータの可搬性を優先しています。

## 🧱 「テナント」の定義
Kintaiにおける**テナント**とは、**オーナー**（個人または企業）を指します。
- 1テナント = 1アプリケーションインスタンス
- 1テナント = 1データベース
- 1テナント = 複数の店舗

## 🚀 デプロイモデル
Kintai SaaSは、これらシングルテナントインスタンスのデプロイを自動化するオーケストレーターとして機能します。

### 1. 共有データベースサーバー（任意）
各テナントは論理的にデータベースが分離されていますが、物理的なデータベースサーバー（例：大規模なMySQLクラスタ）を共有し、各テナントが独自のスキーマ／データベース名を持つ構成も可能です。

### 2. コンテナによる物理的分離
各テナントは専用のDockerコンテナ上で動作し、リソース使用状況やセキュリティ上の脆弱性が単一インスタンス内に閉じ込められます。

## 🔄 ライフサイクル管理
- **プロビジョニング：** DB、`.env`、初期管理者アカウントの自動セットアップ。
- **アップデート：** オーケストレーター経由で管理。テナントは安定版・ベータ版などのチャンネルを選択できます。
- **バックアップ：** 各テナントのデータベースは個別にバックアップされ、きめ細かい復元が可能です。

## 📈 店舗横断ロジック
1人のオーナーが全店舗を単一データベース内で管理するため、複数店舗にまたがる操作もシンプルです：
- **グローバルなユーザー管理：** ユーザーはテナントに所属し、店舗ごとに権限が割り当てられます。
- **一元化されたレポーティング：** 店舗間の人件費や売上の比較は、テナントのDB内でのネイティブなSQLクエリとして実行されます。
- **人員の共有：** 同一テナントが所有する複数店舗にまたがって従業員をシフトに割り当てられます。

## 🚪 退出の自由
このモデルは、私たちのデータ可搬性の基盤です：
- 自社ホスティングへ移行する際、テナントはデータベースのダンプとKintaiのソースコードさえあれば十分です。
- 他ユーザーのデータからの「抽出」作業は一切不要です。
